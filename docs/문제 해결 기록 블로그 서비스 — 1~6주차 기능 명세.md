# 문제 해결 기록 블로그 서비스 — 1\~6주차 기능 명세

Oct 29, 2026 · @molla

## 개요

v1은 6주 안에 알고리즘 문제 풀이 과정을 VS Code에서 기록하고, 근거가 연결된 글로 만들어 Lexical 에디터에서 다듬은 뒤 Ghost에 발행하는 흐름을 완성한다. 대상은 .c·.cpp·.py 한 파일로 문제를 푸는 학생과 개인 개발자다.

이 문서는 2026-10-27 계획서를 대화에서 정한 결정에 맞춰 고친 기능 명세다. 아직 정하지 않은 항목은 추천 기본값으로 채우고, 「추천 기본값으로 채운 항목」 섹션에 따로 모았다.

2026-10-29 GUI 개정: VS Code 확장의 모든 사용자 조작을 사이드바·편집기 탭·설정 폼에서 제공한다. 아래 GUI를 0.2.0에 구현했다. 실제 검증 결과와 남은 Windows Remote WSL·사람 평가 범위는 `EXTENSION.md`와 `WORKLOG.md`에서 구분한다.

기존 계획서에서 바뀐 점:

- 범위: TypeScript 개발, 기능 개발 템플릿, 디버거 수집을 빼고 알고리즘 문제 풀이에 집중
- 순서: 1주차는 최소 기록기와 A/B 파일럿, Ghost 연동은 4주차
- 실행 기록: 확장이 직접 실행하지 않고, 사용자가 통합 터미널에서 실행한 것을 관찰
- 확장 UI: Activity Bar의 Autoblogger 사이드바와 세션·설정 탭이 기본 진입점. 명령 팔레트는 보조 진입점으로 유지
- 에디터: Tiptap 대신 Lexical, Ghost에는 Lexical JSON으로 직접 전송
- 모델: OpenRouter, 데이터를 저장하는 제공자 차단
- 운영: 사용자별 사용 상한과 관리자 대시보드 추가, 모든 데이터 요청은 NestJS 경유
- Ghost: 서비스는 webhook을 수신하지 않고 쓰기 직전에 원격 상태 확인. 기존 Ghost → 정적 사이트 배포 webhook은 유지
- 문제 지문과 저지 제출 결과: 수집하지 않고 후속 Chrome 확장에서 다룸

## v1 범위와 후속 범위

v1은 사용자가 혼자 가입부터 기록, 글 생성, 편집, Ghost 발행까지 끝낼 수 있는 흐름이다. 후속 항목은 구현하지 않지만, 나중에 붙일 때 데이터 구조를 바꾸지 않아도 되게 설계한다.

### v1에 포함

- 계정, 프로젝트, VS Code 확장(Activity Bar, 기록 사이드바, 세션 상세 탭, 설정·연결 탭)
- 저장 스냅샷, 편집 이벤트, 터미널 실행 관찰, 메모·북마크
- 로컬 큐와 서버 동기화
- 세션 타임라인과 실시간 요약
- 시도 구조화, 글 기획·초안·근거 검토
- Lexical 에디터, 근거 패널, 블록 단위 AI 제안, 문서 버전
- Ghost 연결, 초안 저장, 공개, 공개본 업데이트, 공개 취소, 원격 변경 충돌 확인
- Markdown 내보내기
- 사용자별 사용 상한, 관리자 대시보드
- 데이터 삭제·내보내기, 보관 기간 안내

### 후속

- Chrome 확장: 문제 지문 가져오기, 저지 제출 결과 기록
- 기능 개발 템플릿, 여러 파일 프로젝트, 다른 언어
- 디버거 세션, 터미널 밖 실행(Code Runner 출력 창, Run 버튼 등)
- 서비스에서 Ghost webhook 수신, Markdown 가져오기, 문단 잠금, 세션 종료 후 자동 초안
- AI 에이전트 대화 기록 수집
- 팀 기능, 결제, 다른 블로그 플랫폼, 뉴스레터 발송

## 시스템 구성

웹과 확장은 DB나 Storage에 직접 접근하지 않고 모든 데이터 요청을 NestJS API로 보낸다. 긴 AI 작업과 Ghost 전송은 큐를 거쳐 worker가 처리한다.

&#91;embedded content: 시스템 구성 · 구성 요소 8개와 요청 흐름\]

로그인만 웹에서 Supabase Auth로 직접 하고, 받은 토큰은 NestJS가 검증한다.
이메일 발송이 필요 없는 로그인 방식(예: OAuth)을 사용하고, 서비스용 SMTP나 이메일 API를 요구하지 않는다.

| 구성 요소 | 기술 |
| --- | --- |
| 확장 | TypeScript, VS Code API(View Container, Tree View, Webview View/Panel, diff editor, shell integration, SecretStorage) |
| 웹 | Next.js, React, Lexical |
| API | NestJS(TypeScript) |
| 큐와 worker | BullMQ, Redis. API와 같은 저장소, worker는 별도 프로세스 |
| 데이터 | PostgreSQL, Supabase Auth·Storage |
| 모델 | OpenRouter 어댑터, 구조화 응답 검증 |
| 검증 | 단위·통합 검사, Playwright |
| 배포 | 웹 호스팅과 API·worker 컨테이너 분리. 업체와 리전은 미결 |

## 주차별 기능

1주차에 연구 가정을 먼저 확인하고, 2\~4주차에 기록부터 발행까지의 흐름을 완성하고, 5\~6주차에 베타와 평가로 마무리한다. 각 주차는 완료 조건을 통과해야 다음 주차로 넘어간다.

&#91;embedded content: 6주 로드맵 · 주차별 목표와 통과 조건\]

각 상자의 「통과」 줄은 그 주차 완료 조건의 요약이다. 초기 모델과 provider는 확정된 설정을 사용하고, 1주차 결과로 평가 설계를 정한다.

GUI 개정의 구현 순서도 아래 주차별 범위를 따른다. 이미 완료한 기록 엔진·서버 작업은 재사용하고 GUI 완료 조건을 추가로 통과해야 한다. 과거 테스트 통과를 새 GUI의 검증으로 간주하지 않는다.

### 1주차 — 최소 기록기와 A/B 파일럿

목표: 실제 풀이 세션을 기록하고, 기록이 있을 때와 없을 때 초안이 어떻게 다른지 확인한다.

- 확장(로컬 전용)
  - Activity Bar에 Autoblogger 추가. 사이드바에서 작업 폴더 선택, 기록 시작·중지, 현재 파일·수집 상태 확인
  - .c·.cpp·.py 파일 저장 시 스냅샷(내용 해시로 중복 제거)
  - 통합 터미널 실행 관찰: 명령 분류, 종료 코드, 출력 앞부분, 실행 시간, 리다이렉션 입력, 컴파일과 실행의 코드 버전 연결
  - 사이드바의 메모 입력 폼과 북마크 버튼: 대상 파일·줄·시각을 확인하고 저장
  - 세션 목록에서 상세 탭 열기: 로컬 타임라인, 스냅샷·실행 상세, diff 확인
  - 세션 탭의 JSON 내보내기 버튼과 기본 저장 대화상자
- 파일럿
  - C++ 1문제, Python 1문제. 각 30\~60분, 실패가 나올 만한 난이도로 직접 고름
  - 저지 결과는 메모로 남김
  - 초안을 생성하기 전에 중요 사건을 먼저 표시
  - OpenRouter 최소 호출 스크립트로 A(최종 코드만)와 B(기록 포함) 초안 생성. 초기에는 `openai/gpt-6.1-terra`와 `Azure`만 사용
- 완료 조건
  - 명령 팔레트 없이 폴더 선택 → 기록 → 메모·북마크 → 상세 확인 → 중지 → JSON 내보내기 완료
  - 세션 2개의 실행 기록이 모두 올바른 코드 버전에 연결됨
  - 고정된 모델·provider에서 A/B 비교 결과 기록
  - 본 평가 설계와 분기 기준 결정

### 2주차 — 서버, 동기화, 타임라인, 에디터 스파이크

목표: 기록이 서버에 안전하게 올라가고 웹에서 시간순으로 보인다.

- 서버: NestJS API, Supabase Auth 토큰 검증, PostgreSQL 스키마(Project, Session, SourceFile, Snapshot, EditEvent, Run, Memo), 클라이언트 역할의 직접 접근 차단
- 확장 인증: 설정·연결 탭의 연결 버튼 → 브라우저 로그인 → VS Code URI 콜백 → 연결 상태 갱신. 토큰은 SecretStorage에 저장하고 현재 기기 연결 해제도 탭에서 제공
- 확장 고도화
  - 설정·연결 탭: 제외 규칙, 자동 동기화, 주기, 출력 상한, API·웹 주소를 폼으로 제공
  - 사이드바의 연결·동기화 상태, 대기 수, 재시도 버튼. 세션 탭에서 세션별 수신 확인·누락 구간 표시
  - 편집 이벤트: 파일별로 입력이 2초 멈추거나 저장할 때 병합
  - 로컬 큐: 로컬 순번, 서버가 확인한 범위만 완료 처리, 중복 전송은 같은 이벤트로 처리, 빠진 구간 표시
  - 세션 경계: 명시적 시작·중지, 30분 유휴 시 자동 종료
  - 전송 전 비밀값 패턴 필터
- 웹: 로그인, 프로젝트 목록·생성, 세션 목록, 세션 타임라인(파일별 묶음, 스냅샷 diff, 실행 결과, 메모)
- WSL 검증: 원격 extension host에서 파일 접근, 큐 위치, 토큰 저장
- Lexical 스파이크 1\~2일(「글 에디터 상세」의 확인 항목)
- 완료 조건
  - 실제 세션이 서버에 동기화되어 타임라인으로 복원됨
  - 오프라인 후 재연결, VS Code 재시작에서 누락·중복 없음
  - 탭 닫기·재열기와 host 재시작 후 세션 선택·필터·저장 전 메모 복원. 모든 확장 설정을 GUI로 변경 가능
  - Linux와 WSL에서 동작
  - 스파이크 결론: Lexical 확정 또는 Tiptap 전환

### 3주차 — AI 파이프라인, 실시간 요약, 에디터 기본

목표: 세션을 고르면 근거가 연결된 초안이 에디터에 열린다.

- 작업 큐: BullMQ와 Redis worker, 작업 상태를 SSE로 웹에 전달
- 모델 어댑터: OpenRouter 설정 적용(「AI 파이프라인 상세」), 호출마다 ModelRun 기록
- 사용자별 상한 검사: 모든 모델 작업을 등록하기 전에 확인
- 시도 구조화: 파일별로 편집과 실행을 시도 단위로 묶음
- 실시간 타임라인 요약: 실행이나 저장 후 입력이 멈추면 그 변경 묶음을 요약
- 확장 세션 탭: 서버 요약을 원본 사건과 구분해 표시하고, 「웹에서 글 작성」으로 해당 세션·파일을 넘김. 로그인 후에도 선택 문맥 유지
- 글 생성: 기획(제목 후보, 목차, 포함할 사건) → 초안 스트리밍 → 근거 검토(뒤에서 실행, 끝나면 표시 갱신)
- 에디터 기본: Lexical과 Ghost 노드 정의, 블록 ID, v1 블록, 자동 저장, 오른쪽 근거 패널, 왼쪽 사건 목록에서 본문 삽입
- 완료 조건
  - 30분 세션에서 첫 초안이 2분 안에 열리기 시작함(p95 측정 시작)
  - 실시간 요약이 변경 묶음 후 30초 안에 표시됨
  - 근거가 연결되지 않은 주장은 검증 완료로 표시되지 않음
  - 상한을 넘은 사용자의 AI 요청은 거절되고 기록·편집은 계속됨
  - 확장의 웹 이동 버튼이 선택한 세션·파일을 열며, 미동기화·오프라인 때 이유와 동기화 동작을 표시

### 4주차 — 편집 완성, 버전, Ghost 발행

목표: 다듬은 글을 Ghost에 초안으로 저장하고 공개·수정·공개 취소할 수 있다.

## VS Code 확장 GUI 상세

### 사용 원칙과 화면 구성

확장의 모든 기능은 화면에 보이는 버튼·목록·폼으로 접근한다. 명령 팔레트와 단축키는 같은 기능의 보조 진입점으로 남기고, 메모 입력이나 세션 선택에 InputBox·QuickPick을 필수로 거치지 않는다. 폴더 열기·파일 저장·Workspace Trust 등 VS Code 기본 대화상자는 사용한다.

브라우저 로그인은 기존 인증 흐름을 유지한다. 글 기획·AI 생성·본문 편집·Ghost 발행·계정 전체 데이터 관리는 웹에서 수행하며, 확장에는 해당 화면으로 이동하는 버튼을 둔다. 풀이 코드 실행은 사용자가 통합 터미널에서 직접 수행한다.

| 위치 | 화면 | 주요 내용과 동작 |
| --- | --- | --- |
| Activity Bar | Autoblogger | 사이드바 열기. 사용자가 보조 사이드바로 옮긴 배치도 존중 |
| 사이드바 ① | 현재 기록 | 작업 폴더 선택, 시작·중지, 경과 시간, 대상 파일, 수집 여부·제외 이유, 메모 입력·북마크, 상세 열기 |
| 사이드바 ② | 세션 | 작업 폴더별 로컬 세션 목록, 기록 중/종료·시작 시각·대기 수. 선택하면 세션 상세 탭 열기 |
| 사이드바 ③ | 연결·동기화 | 계정 연결 상태, 전체 전송 대기 수, 최근 성공 시각, 수집 가능한 터미널 상태, 지금 동기화·재시도·설정 열기 |
| 편집기 탭 | 세션: 이름 | 상단 세션 정보·동기화 상태·JSON 내보내기·웹에서 글 작성. 내부 탭은 타임라인 / 파일·실행 / 메모·북마크 |
| 편집기 탭 | Autoblogger 설정·연결 | 계정·기기, 수집 제외, 동기화, 고급 연결 설정, 데이터 관리 안내 |
| 기본 diff 편집기 | 코드 변경 비교 | 선택한 스냅샷 또는 편집 전후를 읽기 전용 비교. 원본 파일 덮어쓰기 없음 |
| 상태 표시줄 | 기록 상태 요약 | 기록 중/중지·대기 수·오류 요약. 클릭하면 현재 기록 사이드바로 이동 |
| Output 채널 | 진단 로그 | 연결·동기화 오류 카드의 「진단 로그 보기」에서 열기 |

사이드바는 세 개의 접을 수 있는 뷰로 제한한다. 넓은 내용과 긴 출력은 편집기 탭에 표시한다. 같은 세션은 기존 탭을 다시 열고, 다른 세션은 나란히 열어 비교할 수 있다. 설정 탭은 하나를 재사용한다. 세부 화면 분할과 배치는 이번 개정의 추천 기본값이며, GUI 전환이라는 확정 요구 안에서 사용성 검증으로 조정한다.

```text
Activity Bar     Autoblogger 사이드바       편집기 영역
[Autoblogger]   현재 기록                  [solve.cpp] [세션: 풀이] [설정·연결]
                폴더 선택 · 기록 중        세션 정보 · 내보내기 · 웹에서 글 작성
                [기록 중지] [상세]         [타임라인] [파일·실행] [메모·북마크]
                대상: solve.cpp:24         사건 목록 → 선택한 사건의 코드·출력
                [메모 입력…] [저장]
                [북마크 추가]
                세션 목록                 하단 기본 패널
                연결·동기화                [터미널] [출력: Autoblogger]
```

### 주요 사용자 흐름

1. **첫 사용**: Autoblogger 아이콘 → 폴더 열기/선택 → 수집 대상·제외 규칙 확인 → 기록 시작. 계정 연결 없이도 기록·조회·메모·내보내기를 제공한다. 폴더가 없거나 신뢰되지 않았으면 시작을 비활성화하고 폴더 열기/신뢰 관리 버튼을 보여 준다. 여러 루트가 있으면 사이드바 선택 상자에서 하나를 고른다.
2. **풀이 중**: 코드 편집·저장 → 통합 터미널에서 직접 실행 → 사이드바에 최근 사건 반영 → 필요하면 메모 저장·북마크 추가. 한 extension host에서는 동시에 한 세션만 기록하고 기록 중인 폴더 변경은 중지 후 새 세션 시작으로 처리한다.
3. **기록 검토**: 세션 선택 → 타임라인에서 파일·사건 종류로 필터 → 사건 선택 → 스냅샷·diff·실행 출력·입력·코드 버전 확인. 과거 세션도 오프라인에서 열 수 있다.
4. **연결과 동기화**: 설정·연결 탭에서 계정 연결 → 브라우저 인증 → 확장 복귀 시 상태 자동 갱신 → 대기 이벤트 전송. 실패 원인과 재연결/재시도 버튼은 해당 화면에 남긴다.
5. **종료와 글 작성**: 기록 중지 → 세션 탭에서 기록 확인·JSON 내보내기 → 동기화 완료 후 웹에서 글 작성. 서버에서 세션·파일을 확인할 수 없으면 이동 버튼에 이유를 표시하고 동기화를 안내한다.

### 세션 탭과 입력 동작

- 타임라인은 발생 시각·사건 종류·파일·로컬 순번·전송 상태를 표시하고, 시간순 정렬의 동률은 순번으로 결정한다. 서버 요약은 원본 기록과 구분하고 마지막 갱신 시각을 표시한다. 오프라인에서는 로컬 사건과 마지막으로 받은 요약을 보여 준다.
- 파일·실행 탭은 파일별 스냅샷·편집·실행 목록과 상세를 제공한다. 실행 상세에 명령, 작업 폴더, 종료 상태·코드, 시간, 입력, 출력, 연결된 스냅샷을 표시한다. 출력 잘림·출처 미확인·코드 버전 연결 불가를 숨기지 않으며, 종료 코드 0은 「정상 종료」로만 표시한다.
- 스냅샷·diff는 읽기 전용이다. 「파일 열기」는 현재 작업 파일로 이동하며 당시 코드와 현재 파일이 다를 수 있음을 표시한다. 파일이 사라져도 보존된 스냅샷은 열 수 있다.
- 메모는 여러 줄 입력, 대상 파일·줄 표시, 저장·취소로 구성한다. 북마크도 같은 폼에서 설명을 남긴다. 입력을 시작할 때 코드 에디터의 파일·줄을 고정하고, webview로 포커스가 이동해도 잃지 않는다. 대상 파일이 없으면 세션 메모임을 표시한다.
- 저장 전 문구는 로컬 임시 입력으로 보존한다. 메모 저장·북마크 추가는 기록 중인 세션에서만 가능하다. 종료된 세션의 기존 메모는 읽기 전용이며 저장 전 문구는 복사할 수 있다. 기존 append-only 이벤트 수정·삭제는 추가하지 않는다.
- 기록 중 내보내기는 대기 편집을 반영한 특정 순번까지의 일관된 사본을 만들고, 완료 화면에 해당 범위를 표시한다. 내보내기가 기록 중지를 의미하지 않는다.

### 기존 명령 전체의 GUI 전환

기존 command ID는 유지하되 아래 화면·동작과 같은 서비스 계층을 사용한다. 입력이 필요한 명령은 해당 폼을 열고, `status`는 팝업 대신 사이드바를 연다.

| 기존 명령 (`autoblogger.` 접두사) | 기본 GUI 진입점 |
| --- | --- |
| `start` | 현재 기록 → 기록 시작 |
| `stop` | 현재 기록 → 기록 중지 |
| `note` | 현재 기록 / 세션의 메모·북마크 탭 → 메모 입력 |
| `bookmark` | 현재 기록 / 세션의 메모·북마크 탭 → 북마크 추가 |
| `export` | 세션 상세 → JSON 내보내기. 명령으로 진입하면 세션 목록에서 선택 |
| `connect` | 연결·동기화 / 설정·연결 → 브라우저로 계정 연결 |
| `disconnect` | 설정·연결 → 이 기기 연결 해제 |
| `sync` | 연결·동기화 / 세션 상세의 상태 영역 → 지금 동기화·재시도. 기존과 같이 전체 대기 큐 대상임을 표시 |
| `exclude` | 현재 기록의 대상 파일 / 파일·실행 목록 → 이후 수집 제외 |
| `status` | Activity Bar / 상태 표시줄 → 현재 기록·연결·동기화 보기 |

### 설정·연결 탭

| 기존 설정 (`autoblogger.` 접두사) | GUI와 검증 |
| --- | --- |
| `excludePatterns` | 제외 규칙 목록·추가·제거, 적용 범위와 제외되는 파일 확인. 기본 node_modules·.git·.venv·venv 규칙 유지 |

| `outputLimitBytes` | 숫자 입력, 1,024~262,144바이트, 기본 262,144바이트. 새로 수집할 출력에 적용 |
| `apiUrl` | 고급 설정의 API 주소. 기본 `http://127.0.0.1:4000/api`, 로컬 개발 외 HTTPS 검증 |
| `webUrl` | 고급 설정의 웹 주소. 기본 `http://localhost:3000`, 브라우저 연결에 사용 |

각 폼은 저장·취소·기본값 복원과 필드별 오류를 제공한다. 기존 VS Code configuration을 단일 저장소로 사용하고, 사용자/원격 사용자/작업 영역/폴더 중 실제 지원하는 저장 범위와 유효 값을 표시한다. 현재 파일 제외는 기록 폴더에 적용한다. 다른 설정 화면에서 변경한 값도 반영하며 저장 전 입력과 충돌하면 덮어쓰기 전에 다시 확인한다.

계정 영역은 연결 계정·기기·서버·연결 상태를 표시한다. API 주소 변경 시 기존 인증을 새 서버로 보내지 않고 재연결을 요구한다. 연결 해제는 수집 기록 삭제와 구분하고, 서버 기기 폐기에 실패하면 「로컬 연결 해제 완료 / 서버 폐기 확인 필요」를 표시한다.

파일 제외는 이후 수집에만 적용한다. 서버 관리 제외와 로컬 제외가 함께 적용되면 각각의 출처를 표시하고, 서버 관리 제외를 로컬에서 해제한 것으로 표시하지 않는다. 기존 기록 삭제는 웹 데이터 관리로 연결하며 웹 삭제가 로컬 저널 삭제를 의미하지 않음을 안내한다. 로컬 저널 삭제 기능은 이번 GUI 전환 범위에 추가하지 않는다.

### 상태·오류·복구

기록 상태와 연결·전송 상태를 독립적으로 표시한다. 예를 들어 「기록 중 · 오프라인 · 24개 대기」가 가능하다. 서버 ACK 전에는 전송 완료로 표시하지 않는다.

| 상황 | 화면 동작 |
| --- | --- |
| 세션 없음 / 수집 파일 없음 | 첫 기록 안내 / 지원 확장자·제외 이유와 파일 열기 안내 |
| shell integration 없음 | 「실행 정보 없음」과 설정 안내·터미널 열기. 파일 기록은 계속 가능 |
| 로그인 대기 / 취소 / 만료 | 연결 중 상태, 취소·다시 연결. 기록은 유지 |
| 오프라인 / 서버 오류 | 로컬 기록 유지, 대기 수·최근 성공·오류 원인·재시도 표시 |
| 인증 만료·기기 폐기 | 재연결 필요 표시. 네트워크 오류만으로 토큰 삭제하지 않음 |
| 기록 저장 실패 | 마지막 저장 성공 상태와 실패 원인 표시. 저장되지 않은 사건을 수집 완료로 표시하지 않음 |
| 30분 유휴 종료 / 웹에서 중지·제외 | 중지 이유·시각 갱신. 허용된 경우 새 기록 시작 제공 |
| 탭 닫기 / 숨기기 | 기록·동기화 계속. 재열면 선택한 세션·내부 탭·필터·임시 메모 복원 |
| host 재시작 | 기존 저널 복구 후 화면 재구성. 세션 복구·유휴 종료 여부를 실제 상태대로 표시 |

일상적인 저장·동기화 성공은 화면 안에서 피드백하고, 반복 알림으로 풀이 흐름을 끊지 않는다. 버튼은 진행 중 중복 요청을 막고 비활성화 이유를 표시한다. 오류는 원인과 다음 행동을 함께 제시하며 진단 로그로 이동할 수 있다.

### 구현 경계와 GUI 완료 조건

화면 배치는 VS Code의 [사이드바 지침](https://code.visualstudio.com/api/ux-guidelines/sidebars)을 따른다. 세션 목록은 Tree View, 기록 폼은 Webview View, 세션·설정 탭은 Webview Panel로 구성한다. 복잡한 폼·상세 화면에만 webview를 사용하고 기본 diff·터미널·출력은 재사용한다. webview의 메시지 전달과 상태 복원은 [공식 Webview API](https://code.visualstudio.com/api/extension-guides/webview)를 기준으로 구현한다.

- extension host가 기록·인증·파일 접근·API 호출을 소유하고, UI는 상태와 허용된 action만 주고받는다. Webview에 토큰을 전달하거나 원격 웹 앱을 삽입하지 않는다. CSP, 입력 이스케이프, 메시지 형식·대상 ID 검증으로 코드와 출력을 데이터로 렌더링한다.
- 기록 엔진·저널·ACK·PKCE 계약은 재사용하고, command와 GUI는 동일 action/state 계층에 연결한다. UI를 닫아도 이 계층의 수명은 유지한다. 새 화면은 기존 로컬 저널에서 시작하며 서버 접속을 필수로 하지 않는다.
- 서버 요약 조회는 기존 세션 API/SSE를 이용한다. 「웹에서 글 작성」에 필요한 세션·파일 선택 복원은 웹과 함께 구현해야 하는 새 연결 계약이다. 기존 웹에 해당 딥링크가 구현된 것으로 가정하지 않으며, 서버의 소유자 확인 후 화면을 연다.
- 긴 목록은 점진 로딩/가상화하고, 큰 코드·출력은 상세 선택 시 읽는다. 여러 탭에서 전체 저널을 반복 전송하지 않는다. GUI 버전으로 업데이트한 뒤에도 기존 저널을 변환·초기화 없이 열 수 있어야 한다.

다음은 새로 수행할 검증이며, 기존 headless 기록 테스트 통과와 별도로 결과를 남긴다.

1. 명령 팔레트 없이 10개 기존 명령에 대응하는 모든 동작과 6개 설정 변경을 완료한다. GUI와 보조 명령이 같은 결과를 만든다.
2. 미연결 첫 실행, 멀티 루트 선택, 제외 파일, 정상 기록, 메모·북마크의 대상 파일 유지, 세션 비교·내보내기를 실제 extension host에서 확인한다.
3. 오프라인 수집 → 재연결 → ACK 반영, 인증 실패, 중복 클릭, 유휴·원격 중지에서 사이드바와 모든 열린 탭의 상태가 일치한다.
4. 탭 닫기·숨기기·host 재시작 후 기록 연속성, 선택·필터·임시 메모 복원을 확인한다. GUI 변경 이후에도 기존 기록·실행 버전 연결·재시작 테스트를 통과한다.
5. 키보드만으로 전체 흐름을 수행한다. 포커스 순서·레이블·상태 알림과 밝은/어두운/고대비 테마를 확인하며, 좁은 사이드바에서 필수 버튼이 잘리지 않는다.
6. 10,000개 사건의 합성 세션에서 단계적 로딩·필터·상세 조회를 검사하고 UI 응답 시간·메모리와 환경을 기록한다. 큰 출력 조회 중에도 코드 편집과 기록이 유지된다.
7. Linux host와 Windows 클라이언트 → Remote WSL을 구분해 검사한다. Remote WSL에서 GUI·URI 인증 복귀·저널 위치·SecretStorage·재시작을 실제 조합으로 확인한다.
8. 웹 이동 후 로그인해도 선택 세션·파일이 유지되고, 미동기화·권한 없음·삭제된 세션에는 적절한 안내가 나온다. 베타 설치 문서도 GUI 흐름으로 교체한다.

## 기록 수집 상세

확장은 .c·.cpp·.py 파일의 변화와, 사용자가 통합 터미널에서 실행한 명령을 기록한다. 코드를 직접 컴파일하거나 실행하지 않는다.

### 수집 대상

- 프로젝트 폴더 안의 .c, .cpp, .py 파일만 수집(허용 목록)
- 한 파일 = 한 문제. 시도 묶음과 글의 기본 단위
- 리다이렉션에 쓰인 입력 파일은 편집 추적 없이 실행 입력으로만 스냅샷
- 1MB 초과 파일과 바이너리 제외
- 전송 전에 비밀값 패턴(API 키, 토큰 형태 문자열)을 가림

### 스냅샷과 편집 이벤트

- 세션 시작 시 대상 파일의 초기 스냅샷, 이후 저장할 때마다 파일 전체 스냅샷(내용 해시로 중복 제거)
- 편집 이벤트(2주차부터): 파일별로 입력이 2초 멈추거나 저장할 때 병합해 diff로 저장
- 이벤트마다 로컬 순번, 문서 버전, 발생 시각, 서버 수신 시각, 파일·세션 ID를 가짐
- 한 번에 큰 변경이 들어오면(붙여넣기, 외부 도구, AI 에이전트) 「출처 미확인」으로 표시

### 터미널 실행 관찰

VS Code shell integration이 동작하는 통합 터미널만 대상이다. 명령은 아래 규칙으로 분류한다.

| 종류 | 판별 | 연결할 코드 버전 |
| --- | --- | --- |
| 컴파일 | gcc, g++, clang, clang++로 시작하고 대상 .c·.cpp 파일을 포함 | 컴파일 시작 시점의 디스크 파일 스냅샷 |
| C/C++ 실행 | `./<출력 파일>` 형태. 출력 파일은 `-o` 값, 없으면 a.out | 같은 폴더에서 같은 출력 파일을 만든 가장 최근의 성공한 컴파일 |
| Python 실행 | python, python3로 .py 파일 실행 | 실행 시작 시점의 디스크 파일 스냅샷 |
| 컴파일+실행 한 줄 | `g++ a.cpp && ./a.out`처럼 이어진 명령 | 실행 하나로 기록하고 컴파일 시점 스냅샷에 연결 |
| 기타 | 위에 해당하지 않음 | 기록하지 않음 |

상태는 이렇게 판정한다.

- 컴파일 에러: 컴파일 명령의 종료 코드가 0이 아님. 이어진 명령은 출력의 `파일:줄:열: error:` 형식으로 판단. Python은 출력에 SyntaxError나 IndentationError가 있으면 컴파일 에러로 분류
- 런타임 에러: 실행 명령의 종료 코드가 0이 아님. 128보다 크면 시그널로 표시(예: 139는 세그폴트)
- 정상 종료: 종료 코드 0. 정답 여부는 판단하지 않음
- 판단 불가: 종료 코드를 받지 못함

실행마다 명령, 작업 폴더, 종류, 상태, 종료 코드, 출력 앞부분(최대 256KB, 넘으면 앞뒤만 보존), 리다이렉션 입력 스냅샷, 시작·끝 시각과 실행 시간, 연결된 스냅샷 ID를 저장한다. 직접 타이핑한 입력은 출력과 섞여 분리하지 않는다. 터미널 밖에서 실행한 경우는 기록하지 않고 「실행 정보 없음」으로 표시한다.

### 세션과 동기화

- 세션은 명시적으로 시작·중지하고, 30분 동안 입력이 없으면 자동 종료
- 메모와 북마크는 사이드바 또는 세션 탭의 폼에서 추가하고, 입력을 시작할 때 고정한 파일·커서 위치와 저장 시각을 함께 저장
- 오프라인에서는 로컬 큐에 쌓고, 재연결 시 서버가 수신을 확인한 범위만 완료 처리

## AI 파이프라인 상세

모델은 기록을 해석·구조화·작성·검토하고, 이벤트 정렬·버전·권한·발행은 프로그램이 맡는다. 모든 모델 호출은 OpenRouter를 거친다.

### 단계

| 단계 | 입력 | 출력 | 시점 |
| --- | --- | --- | --- |
| 실시간 요약 | 최근 변경 묶음과 실행 | 한두 문장 요약 | 실행·저장 후 입력이 멈출 때, 30초 목표 |
| 시도 구조화 | 파일별 스냅샷, 실행, 메모 | 시도, 수정, 결과, 근거 ID | 글 생성 시작 시 |
| 글 기획 | 시도 목록, 사용자 목표 | 제목 후보, 목차, 포함·제외할 사건 | 생성 1단계 |
| 초안 작성 | 목차, 사건, 원본 근거, 문체 설정 | 블록과 근거 연결이 있는 초안(스트리밍) | 생성 2단계 |
| 근거 검토 | 주장과 연결된 원본 기록 | 지원됨, 불충분, 충돌, 판단 불가 | 초안 표시 후 뒤에서 |
| 블록 AI 작업 | 선택 블록, 문서 버전, 관련 근거 | 수정 제안 | 사용자 요청 시 |

검토 호출에는 생성 모델의 설명 대신 주장과 원본 근거만 넣는다. 두 모델이 동의해도 정답으로 확정하지 않는다.

### OpenRouter 설정

- 모든 요청에 `provider.data_collection = "deny"`
- 초기 모델은 `openai/gpt-6.1-terra`, provider는 `Azure`로 고정. 실시간 요약, 구조화, 기획, 초안, 근거 검토, 블록 AI 작업, 개발 테스트·파일럿에 동일하게 적용
- 모든 호출에서 provider를 Azure로 제한하고 `provider.allow_fallbacks = false` 적용. 지정된 조합을 사용할 수 없으면 오류로 표시하고 다른 모델·provider로 자동 우회하지 않음. 실제 라우팅 식별자와 사용 가능 여부는 키 제공 후 연동 시 검증
- 구조화 응답: `response_format`의 json\_schema와 `require_parameters = true`
- 평가 호출: `provider.order` 고정, `allow_fallbacks = false`, 모델 ID 고정
- 비용: 응답의 `usage.cost`를 ModelRun에 저장
- 키: 초기 개발·테스트는 사용자가 제공할 $20 테스트 키 사용. 정식 평가·운영으로 확장할 때 키와 예산을 분리
- 모델·provider 설정은 서버에서 관리하고 관리자 페이지에서 변경 가능하게 구현. 변경은 이후 등록하는 작업부터 적용하며 이미 등록된 작업과 ModelRun에는 당시 설정을 유지
- 재시도: 횟수와 원인을 기록하고 최대 횟수를 둠

### 생성 원칙

- 기록된 행동, 사용자 메모(당시 판단), 모델의 사후 해설을 구분해 표시
- 메모가 없으면 「이렇게 생각했다」 같은 1인칭 내면 서술을 만들지 않음
- 문제 지문이 없으면 문제 번호나 제목으로 문제 조건을 추정하지 않음. 「문제와 제약」은 사용자 메모로만 채우고, 없으면 「확인 필요」
- 「정상 종료」를 정답으로 서술하지 않음. 저지 결과는 사용자 메모에 있을 때만 서술
- 중간 요약을 이어 붙이지 않고, 글을 생성할 때 원본 기록을 다시 참조
- 코드와 출력 안의 명령형 문장은 데이터로 취급. 권한이나 발행 동작을 바꾸지 못함
- 모델 호출에는 발행 권한을 주지 않음

### 글 템플릿: 문제 풀이

문제와 제약 → 접근 → 구현 → 실패와 수정 → 정당성·복잡도 해설 → 검증 → 회고 순서를 기본으로, 실제 기록에 맞춰 목차를 조정한다. 실패 없이 풀었으면 구현과 검증 중심으로, 풀지 못했으면 남은 문제와 다음에 확인할 것으로 끝낸다. 템플릿은 설정 데이터(JSON)로 관리한다.

## 글 에디터 상세

에디터는 Lexical로 만들고, Ghost로 보낼 블록에는 Ghost의 Lexical 노드 정의를 그대로 써서 Ghost에 Lexical JSON으로 직접 보낸다. 2주차 스파이크에서 핵심 확인 항목이 실패하면 Tiptap과 HTML 카드 경로로 바꾼다.

### 구성

- UI 출발점: Lexical 공식 Notion형 예제(슬래시 명령, 드래그 핸들)
- 노드: Ghost 노드 정의(@tryghost/kg-default-nodes)와 우리 노드(근거 표시 등). 우리 노드는 Ghost 전송 전에 제거
- 블록 ID: @lexical/extension의 BlockIdExtension(NodeState로 JSON에 저장)
- 발행 미리보기: Ghost 렌더러(@tryghost/kg-lexical-html-renderer)로 HTML 생성
- Ghost 에디터 패키지가 Ghost 모노레포로 옮겨졌으므로 버전을 고정하거나 코드를 복사해 둠

### v1 블록

제목, 문단, 목록, 인용, 코드(언어 지정), diff(언어가 diff인 코드 블록), 이미지. 표는 스파이크 결과를 보고 정한다.

### 화면 배치

| 위치 | 기능 |
| --- | --- |
| 왼쪽 | 목차, 연결된 파일과 시도 목록. 사건을 골라 본문에 삽입 |
| 중앙 | 본문 편집 |
| 오른쪽 | 선택한 블록의 근거(수정 전후 코드, 실행 결과, 메모)와 AI 제안 |
| 상단 | 저장 상태, 버전, 미리보기, 공개 상태, Ghost 작업 상태 |

작은 화면에서는 좌우 패널을 접는다. 이벤트 ID 대신 「두 번째 실행」, 「수정 전 코드」처럼 의미 있는 이름을 보여 준다.

### 근거 연결

- 블록 단위로 연결(EvidenceLink: 블록 ID ↔ 스냅샷·실행·메모)
- 근거가 없거나 사용자가 고친 블록은 「확인 필요」로 표시
- 자동 검토 결과를 「정확함」으로 표시하지 않고, 원본을 열어 직접 판단하게 함

### AI 제안

- 블록 단위로 수락·거절. 블록 안의 변경은 diff로 보여 주기만 함
- 제안을 만든 기준 버전과 현재 버전이 다르면 자동 적용하지 않고 비교 화면을 띄움

### 문서 버전

- 자동 저장은 최근 50개만 유지, 생성·AI 적용·발행 시점은 영구 버전
- 저장할 때 버전을 확인해 여러 탭의 변경을 조용히 덮어쓰지 않음
- 공개본이 있는 글도 별도 편집본을 가짐

### 스파이크 확인 항목(2주차, 1\~2일)

1. Ghost 노드 정의가 쓰는 Lexical 버전에서 BlockIdExtension이 함께 동작하는가
2. 블록 ID와 우리 노드를 뺀 JSON으로 Ghost 글을 만들고 다시 읽었을 때 내용이 같은가
3. 코드(언어 지정), diff, 이미지, 표가 Ghost에서 제대로 렌더링되는가
4. Ghost 렌더러로 만든 미리보기와 실제 Ghost 페이지가 일치하는가

1번이나 2번이 실패하면 Tiptap으로 바꾼다.

## Ghost 저장·발행 상세

Ghost에 쓰는 동작은 모두 Admin API로 하고, 이 서비스에서는 webhook 수신을 구현하지 않는다. Ghost에서 생긴 원격 변경은 쓰기 직전과 글을 열 때 확인한다. 사용자의 기존 Ghost → 정적 사이트 배포 webhook은 별도 경로로 유지한다.

### 기존 연결 환경과 필요한 키(2026-10-29 추가)

- CMS: `https://cms.shinem.dev`, Oracle Cloud에서 운영 중인 Ghost 서버(사용자 제공 정보)
- 공개 사이트: `https://shinem.dev`, Ghost 변경 후 기존 webhook을 통해 정적 페이지로 배포
- 사용자가 CMS에 Custom Integration을 생성한 상태. 연결에는 그 통합의 **Admin API Key**(`id:secret` 형태)를 사용
- Admin API 기준 URL: `https://cms.shinem.dev/ghost/api/admin/`. 공개 사이트 주소를 Admin API 주소로 사용하지 않음
- Content API Key는 공개 콘텐츠 읽기용으로, 초안 작성·수정·공개·공개 취소에 필요한 Admin API Key를 대체하지 못함. 이 서비스의 쓰기 연동에는 Content API Key를 요구하지 않음
- Ghost 반영 성공과 정적 사이트 배포 완료는 구분. `shinem.dev`의 경로 매핑, 빌드 지연, 공개 취소 후 반영 여부는 실제 연동 테스트 때 확인
- 코드·diff·이미지는 Ghost 렌더링뿐 아니라 정적 사이트의 실제 표시도 확인. 기존 webhook과 배포 설정은 그대로 활용

키 종류와 API 주소의 근거: [Ghost Admin API 공식 문서](https://docs.ghost.org/admin-api/), [Ghost Content API 공식 문서](https://docs.ghost.org/content-api/). 실제 서버 연결은 키 제공 후 확인한다.

| 사용자 동작 | 서비스 처리 | Ghost 처리 |
| --- | --- | --- |
| 내 보관함 | 서비스에만 저장, 외부 전송 없음 | 없음 |
| Ghost 초안 저장 | 동기화 작업을 만들고 결과 표시 | draft 생성 또는 수정 |
| 공개 | 선택한 문서 버전으로 발행 작업 생성 | published, public으로 저장 |
| 공개본 업데이트 | 편집본과 공개본 차이를 확인하고 새 버전 전송 | 같은 글 ID로 수정 |
| 공개 취소 | 원격 결과를 확인한 뒤 미발행으로 표시 | draft로 전환 |
| 연결 해제 | 이후 동기화 중단 | 이미 있는 글은 삭제하지 않음 |

### 규칙

- 전송 형식: 블록 ID와 우리 노드를 뺀 Lexical JSON. Tiptap으로 바꾸면 HTML 카드로 감싼 HTML
- 충돌: 마지막 동기화 때의 updated\_at과 원격 updated\_at이 다르면 비교 화면. 사용자의 원격 변경을 덮어쓰지 않음
- 이미지: 발행할 때 Ghost 이미지 API로 업로드하고 URL을 바꿈. 우리 Storage URL을 글에 남기지 않음
- 발행 worker: 선택한 불변 버전만 읽음. 응답이 유실되면 원격 상태를 확인한 뒤 재시도하고, 새 글 생성을 무조건 반복하지 않음
- 공개 취소는 Ghost에서 실제로 성공해야 완료로 표시
- 저장 정보: Ghost 글 ID, 마지막 동기화 버전, 원격 updated\_at, 발행 URL
- 연결: 사이트 주소와 Admin API 키. 키는 콘텐츠 전반을 다룰 수 있으므로 암호화 저장하고, 전용 통합을 만들고 폐기하는 방법을 안내
- 사이트 주소와 원격 이미지는 외부 URL 검증을 거침
- 코드 구문 강조는 Ghost 테마에 따라 다르므로, 설정 화면에 코드 삽입 스니펫을 안내
- 뉴스레터 발송은 하지 않음
- 테스트 사이트: Docker의 격리된 Ghost에서 자동화 검증 후 기존 `cms.shinem.dev`와 `shinem.dev` 경로의 연동을 확인. Ghost(Pro) 체험판은 필수 준비 항목에서 제외

- 사용 중인 키의 남은 한도는 `GET /api/v1/key`로 조회해 대시보드에 표시

## 계정·보안·데이터 관리

로그인만 Supabase Auth로 하고, 데이터 접근과 권한 확인은 모두 NestJS가 한다.

### 인증과 접근

- 웹: Supabase Auth로 로그인하고, NestJS가 토큰을 검증
- 확장: 브라우저 로그인 → VS Code URI 콜백 → SecretStorage에 토큰 저장. 웹 설정 화면에서 기기별로 폐기
- 소유자 검증: API와 worker 모두에서 확인. worker는 서비스 권한으로 돌아도 작업의 소유자를 확인
- RLS: 켜 두되 anon, authenticated 역할에는 정책을 주지 않아 직접 접근을 막음
- 파일 업로드: NestJS가 소유자를 확인하고 서명 URL을 발급, 클라이언트가 Storage에 직접 업로드
- 작업 상태: NestJS가 SSE로 전달(Supabase Realtime은 쓰지 않음)

### 비밀과 외부 입력

- OpenRouter 키는 서버에만 보관하고 브라우저나 확장에 넣지 않음
- Ghost Admin API 키는 암호화 저장
- Ghost 사이트 주소와 원격 이미지는 외부 URL 검증
- 코드와 로그 안의 명령형 문장은 분석 대상 데이터로만 취급

### 데이터 관리

- 기록 중지와 파일 제외는 확장 사이드바·파일 목록과 웹 양쪽에서 가능
- 삭제: 원본, 파생 요약, 근거 연결, 파일까지 추적해 지움. Ghost에 이미 발행된 글과 백업의 처리 범위는 따로 안내하고 고르게 함
- 내보내기: 글은 Markdown, 기록은 원본 JSON
- 보관 기간(추천 기본값): 원본 기록 90일, 글과 버전은 사용자가 지울 때까지
- 개인정보 처리방침과 국외 이전 고지(모델 API, 호스팅 위치)는 5주차 베타 전에 작성

| PublicationJob | 문서 버전, 목표 상태, 원격 글 ID, 시도 횟수, 결과 |
| SyncState | 마지막 동기화 버전, 원격 updated\_at, 충돌 정보 |

생성, 편집, 공개, 동기화 상태는 각각 따로 관리한다. 「생성 완료」를 「발행 완료」로 표시하지 않는다.

## 평가 계획

1주차 파일럿으로 연구 가정을 먼저 확인하고, 본 평가 설계와 분기 기준은 그 결과로 정한다. 본 평가는 6주차에 세션 10개(본인 5, 베타 5)로 한다.

### 개발 테스트용 기존 기록과 mock 데이터(2026-10-29 추가)

- 사용자는 과거 유사한 확장 `ps-blogself`를 만들어 사용했다. 확장 스토리지 등에 코드 작성 기록이 남아 있을 가능성이 있으나 존재·위치·형식은 아직 확인하지 않았다
- 컨텍스트 오염을 방지하기 위해 지금은 해당 확장의 소스나 스토리지를 조사하지 않는다. 구현 중 실제 테스트 데이터가 필요한 시점에만 기록 위치와 형식을 확인한다
- 가져올 대상은 코드 작성 데이터로 한정한다. 기존 서비스의 구현·프롬프트·생성 글·대화 기록은 참고하거나 가져오지 않는다. 형식 확인도 기록 해석에 필요한 최소 범위로 제한한다
- 원본은 보존하고 복사본을 현재 Session·SourceFile·Snapshot·EditEvent·Run·Memo 형식에 맞게 변환한다. 실제로 남아 있는 필드만 옮기고, 없는 실행 결과·시각·버전 연결은 추정으로 채우지 않는다
- 변환 시 원본 식별자와 변환 후 식별자의 대응, 시간순서, 코드 버전 연결, 누락 필드를 기록한다. 비밀값을 가리고 재현 가능한 테스트 fixture로 사용한다
- 기록을 찾을 수 없거나 테스트에 쓸 수 있는 형태가 아니면 mock 데이터를 만들어 동기화·타임라인·생성·편집 흐름을 테스트한다. 데이터 탐색 때문에 구현과 테스트를 중단하지 않는다
- 이식 기록과 mock 데이터는 출처를 구분해 표시하고 개발 테스트에 사용한다. 정식 채점이나 동의받은 베타 세션으로 계산하지 않으며, 이를 이용한 테스트 통과와 실제 파일럿·본 평가 완료를 구분해 보고한다

### 연구 질문

개발 기록에 근거한 생성·편집 기능이 실패 과정의 누락과 근거 없는 의도 서술을 얼마나 줄이는가. 결과가 나오기 전까지는 가설로 쓴다. MCS의 Claim에서 「최종 코드에는 중간 시도가 드러나지 않는다」는 Motivation으로 옮긴다(추천 기본값).

### 파일럿(1주차)

- 세션 2개(C++ 1, Python 1). 생성 전에 중요 사건을 먼저 표시
- A(최종 코드만)와 B(기록 포함 자유 생성)를 동일한 `openai/gpt-6.1-terra` / `Azure` 설정으로 생성
- 결과물: 누락과 근거 없는 서술 사례, A/B 비교, 본 평가 설계와 분기 기준. 초기 범위에서는 여러 모델을 비교하지 않음

### 본 평가 설계(원안, 파일럿 후 확정)

| 조건 | 방법 |
| --- | --- |
| A | 최종 코드만으로 생성 |
| B | 시간순 기록을 추가해 자유 생성 |
| C | 같은 기록으로 구조화, 근거 연결, 검토 |
| C − 검토 | C에서 검토만 뺀 추가 조건 |

- 공통 조건: 같은 모델, B와 C에 같은 메모, 문제 지문은 연구자가 직접 입력, provider 고정. 글 길이, 입력 범위, 모델 설정을 기록

- 평가자에게는 조건을 숨기고 순서를 섞어 보여 줌

### 지표

- 중요 사건 보존율: 기준 사건(결과가 바뀐 실행, 되돌린 변경, 메모 지점, 원인이 확인된 지점, 최종 수정) 중 글에 정확히 들어간 비율
- 근거 없는 서술 비율: 원자적 사실 단위로 나눠(모델이 1차, 사람이 검수) 기록이나 메모로 뒷받침되지 않는 비율
- 근거 연결 정확도: 연결한 기록이 그 주장을 실제로 지지하는 비율
- 기술 해설 정확도: 코드 동작, 복잡도, 정당성 설명의 오류
- 편집 부담: 중요한 사실 수정 건수(정량), 편집 시간과 체감 부담(인터뷰)

사건 보존율과 근거 없는 서술 비율은 항상 함께 보고해, 짧게 써서 오류를 줄이는 경우를 구분한다. 세션 10개의 결과는 경향으로만 보고, 개발자 전체로 일반화하지 않는다.

### 제품 지표
