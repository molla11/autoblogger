## 정식 평가 절차

1. 동의를 받은 본인 5개·베타 5개 실제 세션을 준비한다. mock이나 설정 파일을 실제 풀이 기록으로 계산하지 않는다.
2. 생성 전에 중요 사건을 표시하고 원본 ID·코드 버전·누락 필드를 확인한다. 파일럿 C++/Python 각 1개에서 누락·근거 없는 서술 사례를 검토한 뒤 비교 조건과 분기 기준을 확정한다.
3. `[{sessionId,provenance,events,importantEvents:[{id,label}]}]` JSON을 준비한다. 필드가 없는 실행 결과나 풀이 의도를 추정해서 채우지 않는다.
4. `pnpm exec tsx scripts/evaluate.ts --all --repeat=3 --input=입력.json`으로 생성한다. 현재 도구는 A/B/C/C−검토를 지원하며 모두 같은 모델/provider를 사용한다.
5. 검토자에게 `blind-review.json`과 필요한 원본 근거를 제공하고 조건을 담은 `manifest.json`은 숨긴다. 생성 전에 작성된 `annotations.json`을 기준으로 평가한다. 출력 자체의 서식 차이까지 완전히 감출 수 있는 설계는 아니다.
6. 사실을 원자적 주장으로 나누고 사람이 원본과 대조한다. 사건 보존율·근거 없는 서술 비율·근거 연결 정확도는 0~1, 기술 오류는 건수, 편집 시간은 분으로 기록한다. 중요한 사실 수정 건수와 체감 부담은 별도 인터뷰에 남긴다. 독립 검토자가 일부를 교차 채점하고 불일치를 기록한다.
7. `pnpm exec tsx scripts/score-evaluation.ts .data/evaluations/실행디렉터리`로 집계한다. null이 남은 항목은 미채점으로 보존하며 0점으로 바꾸지 않는다. 사건 보존율과 근거 없는 서술 비율을 함께 보고한다.
8. 실제 30분 이상 세션에서 첫 초안·요약 지연을 추가 측정한다. 10개 세션의 결과는 기술적·서술적 비교로 제한하고 전체 개발자에게 일반화하지 않는다.

기존 `ps-blogself` 탐색에서는 코드 작성 기록을 찾지 못했다. WSL/Windows workspace storage의 설정만 확인했으며 이전 구현·프롬프트·생성 글·대화는 읽지 않았다. 현재 fixture는 명시적으로 생성한 mock이다.
